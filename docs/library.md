# Using agent-shim as a library

`agent-shim` (and `claude-use`, its former name, published as an identical package) ships a library alongside the CLI: `import { ... } from "agent-shim"`, ESM or CommonJS, with type declarations. The library exposes the parts that are pure over facts and ports passed in, so another tool can call them in process instead of shelling out. It never imports `commander` or `@clack/prompts`, and the build fails if that stops being true.

## What it exposes

| Group | Entry points | Use it to |
|---|---|---|
| State root | `resolveAgentShimHome`, `resolveLayoutPaths`, `buildLayoutPaths`, `resolveClaudeHome`, `LayoutPaths` | Find where agent-shim keeps its state, with the same rules as the CLI (`AGENT_SHIM_HOME`, then `~/.agent-shim`, then an existing `~/.claude-use` used in place) |
| Configuration schemas | `IdentitySchema`, `ConfigProfileSchema`, `ProviderSchema`, `PoolSchema`, `DirectoryRulesSchema`, `GlobalConfigSchema`, `CredentialSchema`, `CategoryMapSchema` and the rest, each with its inferred type | Validate or generate a config file with the definitions the CLI itself uses; `z.toJSONSchema(Schema)` produces a JSON Schema |
| Resolution and farm sync | `resolveDecisions`, `buildEntryFacts`, `resyncFarm`, `recoverFarm` | Decide what an identity shares for a directory, and build or repair its farm, over an injected filesystem |
| Routing | `startConnectServer`, `ensureFrontDoor`, `runFrontDoorSupervisor`, `ensureHeadroom`, `runSupervisor` | Run or attach to the front door and the headroom daemon |
| Remote Control | `createRcSessionTracker`, `observingRoutedRoute`, `injectRcUserMessage`, `answerRcControlRequest`, `interruptRcSession`, `setRcSessionModel`, `setRcSessionPermissionMode` (with `RC_PERMISSION_MODES` and `isRcPermissionMode` for its mode enum), and the wider verb family `endRcSession`, `getRcSessionUsage`, `getRcSessionContextUsage` (with `RC_CONTEXT_USAGE_DETAILS` and `isRcContextUsageDetail`), `readRcSessionFile` (with `RC_READ_FILE_ENCODINGS` and `isRcReadFileEncoding`), `suggestRcSessionFiles`, `sendRcKeepAlive`, `getRcSessionMcpStatus`, `reconnectRcSessionMcpServer`, `authenticateRcSessionMcpServer`, `submitRcSessionMcpOAuthCallbackUrl`, each built on `buildRcControlRequestPayload` (and `buildRcKeepAlivePayload` for the envelope-less liveness payload), `realRcEventDial`, `createRcControlHandler`, `frontDoorRcControl`, `createRcCredentialStore` | Track the `cse_` sessions whose traffic a door serves, their pending control requests and worker status, inject a prompt into one, answer a pending request, and send the client half's own control requests into one (interrupt, model, permission mode, end-session, the usage and context queries, read-file, file-suggestions, keep-alive, and the mcp_* family), each by replaying the protocol's client-half write over the door's own dials and surfacing the minted request id the worker's `control_response` echoes, with the observed client credential persisted per session so a later door generation can still attach and write, and the stream's sequence cursor persisted beside it so that generation also resumes the client read stream from where the last one left off instead of at its head |
| Remote Control client read stream | `createSseParser`, `parseRcStreamEnvelope`, `createRcEventFanout`, `createRcStreamHub` (with `RC_STREAM_BACKOFF_MS`, `realRcStreamDial`, and the `RcStreamDial`/`RcStreamHub`/`RcEventFanout` shapes), `RcStreamEnvelopeSchema`, `RcStreamEventSchema`, `RcPermissionModeSchema`, and the rate-limit payload family `RcRateLimitInfoSchema`, `RcRateLimitWindowSchema`, `RcLiveRateLimitSchema` with `rcRateLimitInfoOf` and `createRcLiveUsage` | Hold the client read stream open as the door's own attached client: parse the SSE wire, read the envelopes, fan the events out to every subscriber, and attach one stream per tracked session with the documented presence call and resume pair, over an injected dial. `createRcLiveUsage` subscribes to the door's event backbone and keeps each session's latest `rate_limit_event` (the account's unified rate-limit windows, `resetsAt` in unix epoch seconds) as the live quota state the control plane's `usage.live` serves, exactly as fresh as the last turn a session completed |
| Self-hosted Remote Control | `createRcSelfHostSurface` with `rcSelfHostFromEnv` and `RC_SELF_HOST_ENV` (plus the surface's own derived constants and shapes, and the `webSearch` injection point a real search backend answers through), `realRcWebFetch` with `fetchThroughWebProxy`, `isPrivateAddress`, `rcWebFetchAllowsPrivateFromEnv` and the `RC_WEB_FETCH_*` names (the worker's web-fetch proxy and its bounds, over the door's own interception-proof dials), `mintRcSelfHostCredential` with `readRcSelfHostRecord` and the `RC_SELF_HOST_RECORD_*` names, and the late-targeted `lateRcEventDial`/`lateRcStreamDial` beside `realRcEventDial`/`realRcStreamDial` and the `ConnectLocalSurface` the connect config takes | Serve the CCR session family on the door itself (the opt-in mode where a session activates Remote Control with no Anthropic credential anywhere), including the worker's web-fetch and web-search proxies, mint and read back the local credential that authenticates it, and point the door's own client half at its own transparent surface once that has bound |
| Remote Control typed API | `createRcApiRouter`, `createRcApiNodeHandler`, `frontDoorRcApiClient` (with `RC_ORPC_PATH_PREFIX`) | Serve the same Remote Control operations as a typed oRPC API beside the bespoke control routes, authenticated by the same per-generation control token, and consume it from a CLI-shaped TLS-pinned client, `rc.subscribe` streaming the attachment's fan-out; the one node handler also serves every route-annotated procedure as plain REST under a `/rest` namespace, with the OpenAPI document at `/__agent-shim/orpc/openapi.json`, for consumers with no TypeScript client |
| Door control plane | `createControlApiRouter` with its schemas, `createDoorApiRouter`, `createDoorApiNodeHandler`, `frontDoorApiClient` (with the shared `doorApiAuth`, `doorApiNodeHandlerOf` and `frontDoorApiLink` the Remote Control API also rides), `collectFrontDoorStatus` and `FrontDoorStatus`, the `controlSchemas` (`UsageListOutputSchema`, `UsageLiveOutputSchema`, `UsageWindowsInputSchema`, `UsageWindowsOutputSchema`, `FrontDoorStatusOutputSchema`, `FrontDoorSessionsOutputSchema`, `CheckRunInputSchema`, `DoctorRunOutputSchema`) and `CheckReportJsonSchema` | Serve and consume the door's general control plane beside Remote Control on the one oRPC mount, read-only, behind the same per-generation control token: `usage.list`, `usage.effectiveWindow` (the per-identity snapshots and their quota windows as `effectiveWindow` reads them, at the door's own clock) and `usage.live` (the live rate-limit observations the event backbone files off the Remote Control client stream, per session and door-wide, each stamped with when the door observed it), `frontdoor.status` and `frontdoor.sessions` (exactly what `agent-shim frontdoor status` collects), `check.run` (the report `check --json` prints, over an absolute path), `doctor.run`, and `pool.pick` (the ranking `pool pick --json` prints for one pool exactly as a launch from the named absolute directory would make it, an unknown pool refused naming the live ones). `frontDoorApiClient` is the whole-door client, with the `rc.*` procedures beside the control plane |
| Door event backbone | `createDoorEventHub`, `rcFanoutOnDoorHub` (with `DOOR_EVENT_BUFFER_EVENTS` and the `DoorEventHub`/`DoorEventPublisher`/`DoorEventStream` shapes), `DoorEventSchema`, `DoorEventSourceQuerySchema`, `LaunchLifecycleEventSchema`, `DoorHealthEventSchema`, `QuotaExpiringEventSchema` and the `UsageChangeEvent` payload type with the `DOOR_EVENT_SOURCE_RC`/`LAUNCH_EVENT_SOURCE`/`USAGE_EVENT_SOURCE`/`DOOR_HEALTH_EVENT_SOURCE`/`QUOTA_EXPIRING_EVENT_SOURCE` tags, `createLaunchEventPublisher`, `createDoorHealthPublisher`, `createQuotaExpiringPublisher`, and the `createEventsApiRouter` the whole-door mount serves beside the others | Run the door's generalised event fan-out in process: register sources, publish source-tagged events stamped with a per-source sequence, and subscribe synchronously or through the bounded drop-oldest pull bridge whose gaps that sequence make visible; wrap the Remote Control fan-out on as the backbone's first publisher, turn the session registry's register, prune and end moments into events, publish every usage snapshot the store writes (the usage source), the supervisor's own state transitions (the door source), and each unspent window entering its final span (the quota-expiring source, computed from the same snapshots the pool ranking reads); `events.subscribe` serves it on the whole-door mount |
| Usage | `readUsageSnapshot`, `listUsageSnapshots`, `UsageSnapshotSchema`, `effectiveWindow` | Read the per-identity usage snapshot a statusline shows, and read one of its windows as agent-shim does (a window past its `resetsAt` counts as empty, so a consumer keeps no copy of that rule) |
| Pool ranking | `rankPool`, `planOf`, `collectPoolPick`, `PoolPickReportSchema`, `PROMPT_CACHE_TTL_MS`, with the types `RankPoolInput`, `PoolMember`, `NestedContribution`, `PoolRanking`, `Candidate`, `StickyPick`, `PlanClass`, `PoolPickReport` | Choose an identity from a pool the way `agent-shim pool pick` and a pool launch do. `rankPool` is pure over its input: each member's usage snapshot (`UsageSnapshotSchema`), account metadata and recent log records, the clock, and the directory's last pick; a member may instead stand for a nested `pool:<name>` entry, contributing that pool's pick (with the composition in its reasons) or its refusal; it returns every member in pick order with its class, score and reasons. `collectPoolPick` reads this machine and returns the report `pool pick --json` prints, validated by `PoolPickReportSchema` (also published as `schema/PoolPickReport.schema.json`). It reads the unified five-hour and seven-day windows only |
| Conditions | `evaluateWhen`, `matchBranch`, `ConditionContext`, `WhenEvaluation` | Evaluate a rule's or entry's `when` (branch, environment and, when the context carries an entry's facts, its age and size) with the cascade's own semantics, for example over rules from `listDirectoryRules`. A `when` is either the object form or a trilean predicate tree over the same facts, and the evaluation is three-valued: definite, or indeterminate naming what was missing. The context also carries the pool facts a member entry's policy condition reads (`quota.*`, `session.*`) and the request facts a provider route's condition reads (`request.*`, `provider.<name>.*`), so one evaluator serves the cascade, the pool ranking and request routing |
| Guard | `detectAmbientCredential`, `evaluateAmbientCredentialGuard` | Check whether an environment variable would override an identity's login |
| Configuration management | `addIdentity`, `listIdentities`, `setIdentityCredential`, `createProfile`, `setProfileCategories`, `addProvider`, `readProvider`, `addPool`, `addDirectoryRule`, and the rest of the `*Store` modules | Create, read, list and change identities, configuration profiles, providers, pools and directory rules under a state root, exactly as the CLI does; each takes the `LayoutPaths` root and throws a typed error such as `IdentityNotFoundError` |
| Reports | `collectCheckReport`, `collectDoctorReport`, `runCheck`, `runDoctor`, `formatCheckReport`, `formatDoctorReport`, `checkReportToJson` | Ask what a launch in a directory would share or hide (`check`), or audit the whole state root (`doctor`), and get a report object back. The `collect…` functions read this machine; `runCheck` and `runDoctor` take the facts as parameters, so they run over fakes |
| Launching | `prepareClaudeLaunch`, `LaunchRefusedError`, `prepareLaunch`, `runLauncher`, `spawnClaude`, `LaunchPlan` | Resolve a launch for a directory (the identity, provider, credential, sharing rules and flags the command line would apply) and get back the `claude` binary, arguments and environment to spawn yourself. It performs the effects the child depends on (the identity's farm resync, and bringing up and registering with the front door and headroom, which needs `agentShim`, the path of the agent-shim executable, because this process is not it); call `release` on the plan when the child exits, which is the ordering `runLauncher` and `spawnClaude` encode so an embedder does not have to: the former plans, spawns and releases in one call, the latter takes a plan's parts directly. A refusal throws `LaunchRefusedError` with the launcher's message. `prepareLaunch` is the same over injected ports |
| Errors | `CliError`, `UsageError`, `EXIT_FAILURE`, `EXIT_USAGE` | Tell an expected, user-facing failure from a crash |

## The typed API's versioning

The door's typed API (Remote Control, the control plane and the events surface, over RPC and REST alike) carries no path version: its contract is versioned by the package release, because every procedure, route annotation and schema change rides a semver release of agent-shim, and the OpenAPI document served at `/__agent-shim/orpc/openapi.json` states the running version as its own `info.version`, so a consumer can always name which contract it dialled. A breaking change to the served surface would arrive as a new namespace served beside `/rest` (the same separation that keeps the REST routes from the RPC protocol's procedure paths), introduced in the release that breaks and documented there; no second version is pre-built.

## Example

```ts
import { IdentitySchema, resolveLayoutPaths } from "agent-shim";
import { readFileSync } from "node:fs";
import path from "node:path";

const paths = resolveLayoutPaths();
const identity = IdentitySchema.parse(JSON.parse(readFileSync(path.join(paths.identitiesDir, "work", "identity.json"), "utf8")));
```

## What is not in the library

What stays CLI-only is the command-line surface itself: the interactive setup wizards and prompts, the `commander` command tree (`buildProgram`) and its output formatting, and shell completion. Launching is not CLI-only: `prepareClaudeLaunch` resolves a launch and returns what to spawn, and `runLauncher` and `spawnClaude` carry it out over injected ports. Anything the library does not cover can be scripted through the CLI, whose `list`, `show`, `check`, `doctor` and mutating (`add`, `set`, `remove`, `use`) commands all accept `--json`.

The export list is guarded by `src/index.test.ts`, so removing or renaming an entry point is a deliberate, visible change.
