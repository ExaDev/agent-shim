# Claude Code service contracts

What the Anthropic services that Claude Code reaches accept and answer, for the features that need a claude.ai login or a first-party endpoint. It is the reference for any agent-shim component that answers one of these services itself (the front door already answers a few), and it records the evidence for each shape so a change in the client can be told from a mistake here.

## How these contracts were established

Each section names its evidence:

- **Capture**: the traffic of a real signed-in session through the interception rig (`docs/rc-interception-rig.md`), read with `scripts/decode-http-capture.mts --contract`, which folds every sample of an endpoint into one shape. Optional keys carry a `?`, a type list means samples disagreed, and an object keyed by names collapses to `<key>`. Nothing in a shape comes from a single sample's value except an enumeration seen to vary across several.
- **Client**: the bundled client code of the Claude Code CLI, read where a feature could not be exercised on the account used (a plan the account lacks, hardware, an organisation policy, or a submission that would reach Anthropic as real data). A client contract says what the client sends and validates; it cannot say what the server does beyond that.

Shapes are of the contract the server presented to one account on one client version, so a field absent here may exist for another plan, and a field present may be absent for another. The `anthropic-beta` header values are part of each contract: a request without the named beta is a different request.

Every request below carries `authorization: Bearer <OAuth access token>` unless stated. The OAuth token's scopes decide which routes accept it: `user:profile`, `user:inference`, `user:sessions:claude_code`, `user:mcp_servers`, `user:file_upload`, `user:plugins`, `org:create_api_key`. A route reached with a token lacking its scope is refused by the server, not by the client.

## What gates each feature

The client decides before it calls: a feature that needs a login is switched off with a logged reason, not tried and refused. The conditions, read from the client's own gate messages and confirmed by launching the CLI with debug logging under each posture:

| Posture | What the client does |
|---|---|
| OAuth login with the full scope set | everything below is reachable |
| `ANTHROPIC_AUTH_TOKEN`, an API key or `apiKeyHelper` in the environment (env-token mode) | claude.ai connectors are disabled ("API-key auth precedence active"), Claude in Chrome is disabled ("OAuth token has no scope accepted by /api/oauth/validate"), bootstrap is skipped ("no usable OAuth, WIF, or API key"), the feature-flag fetch runs on defaults, Remote Control refuses |
| `ANTHROPIC_BASE_URL` naming a host other than the Anthropic API | Remote Control and the organisation policy lookups (managed settings, the Chrome policy) are off |
| Bedrock, Vertex or Foundry | bootstrap, telemetry, the feature-flag fetch, the Files API, the connector proxy, channels, `/feedback`, cross-machine messaging, Ultrareview and cloud sessions are off |
| a plan without the feature | the server refuses: self-hosted environments need Team or Enterprise, voice and Teleport need a Claude account, channels need `channelsEnabled` from the organisation |

Per feature, the gate message the client prints and the posture it keys on:

| Feature | Gate |
|---|---|
| Remote Control | first-party API host and OAuth login ("Remote Control requires a claude.ai subscription"); refused in env-token mode |
| Cloud sessions, `--cloud` | OAuth login ("Cloud sessions require a claude.ai login"); not available on third-party providers |
| Teleport | "Teleport requires a Claude.ai account" |
| Ultrareview | "Ultrareview requires a Claude.ai account"; "unavailable on third-party providers" |
| Artifacts | "Artifacts need a claude.ai login" |
| Claude in Chrome | "Claude in Chrome requires a claude.ai subscription" and an OAuth scope the validate route accepts |
| Voice mode | "Voice mode requires a Claude.ai account", and a recorder (SoX) on the machine |
| claude.ai connectors | OAuth login with `user:mcp_servers`; disabled on third-party providers and in API-key mode |
| Files API and file upload | "unavailable on third-party providers (data-residency)"; the upload route needs `user:file_upload` |
| Channels | not available on Bedrock, Vertex, Foundry or other third-party providers; needs the organisation's `channelsEnabled` |
| `/feedback` | disabled for third-party providers, by organisation policy or by environment variable |
| Cross-machine messaging | not allowed on a third-party provider or with non-essential traffic disabled |
| Plan limits in `/usage` and the statusline | an OAuth profile scope; null for an API key, Bedrock, Vertex or a missing profile |
| Prompt-cache lifetime | one hour on a Claude subscription within its limits, five minutes on an API key, Bedrock, Vertex or Foundry |
| Managed settings and policy limits | fetched only with first-party credentials and the default base URL; `forceLoginMethod` and `forceLoginOrgUUID` in managed settings refuse a session whose login does not match |

## Cloud sessions

`claude --cloud <description>` runs a session on Anthropic's infrastructure against a GitHub repository, and `claude --teleport <id>` brings one back. Evidence: capture, from a session that ran to completion and one on a public repository, then a teleport of each.

## Artifacts

An Artifact is a page the CLI publishes, which the claude.ai viewer serves in a sandbox. Evidence: capture of a publish, an update, an update that declared a capability, a read, a list and the live sync socket.

### Publishing

All calls carry `anthropic-beta: oauth-2025-04-20` and the client headers `x-frame-client-version`, `x-frame-platform`, `x-frame-surface`, `x-frame-session-id`, `x-frame-cp`.

- `GET /api/frame/contract/latest` answers `{version, capabilities[], core[], claude, features{mcp{host}}}`: the published contract version and the capability names it serves.
- `GET /api/frame/contract/{version}/{name}`: the page runtime's contract, served as TypeScript declarations (`artifact.d.ts`, `assets.d.ts`, `claude.d.ts`, `comments.d.ts`, `db.d.ts`, `downloads.d.ts`, `files.d.ts`, `mcp.d.ts`, `permissions.d.ts`, `room.d.ts`, `sample.d.ts`, `self.d.ts`, `user.d.ts`) and a text `prompt` that tells a model how to write a page. The declarations are the authoritative type of each capability (see "The page runtime" below); fetch them from the service rather than copying them, since they are versioned.
- `POST /api/frame/deploy/prepare` with `{entrypoint: "cli"}` answers `{slug, read, missing[]}`: a fresh slug and the URL the page will be read from.
- `POST /api/frame/deploy/direct?attempt_id=<uuid>` publishes. Request `{slug, title, description, icon, content, template, entrypoint, publish_context, request_id, baseVersion?, capabilities?{db}, contract?}`. Answer `{slug, title, version, seq, history[], read, contract, minContract, preferredContract, favicon, icon, public, owned, outside_writer, owner_account_id, owner_in_your_org, owner_workspace, typeInstance, updated_at, appliedOver?, capabilities?}`. Republishing the same slug with `baseVersion` is the update path; `appliedOver` names the version it replaced.
- `POST /api/frame/track` with `{event_name, slug, via, mode}` answers `204`; the modes seen were the auto-open outcomes.
- `GET /api/frame/read/{slug}` answers `{contract, public, owned, outside_writer, owner_account_id, owner_in_your_org}`; `GET /api/frame/{slug}?via=...` answers the record the viewer needs: the file list (`{path, contentType}`), the permissions record, an asset token and a sync token (both credentials), the capabilities and the contract version.
- `POST /api/frame/db/agent` with `{slug, verb, args{path}}`: the database access of the owner's agent (the `read_db` and `write_db` actions); the answer to the existence check was `{exists, public, owned, outside_writer, owner_account_id, owner_in_your_org}`.

### The artifacts MCP server

`POST /api/artifacts/mcp`, JSON-RPC over HTTP with headers `mcp-method`, `mcp-protocol-version` and the `x-frame-*` set. The client first sends `server/discover` (answered `404`, which it treats as "not a newer server"), then `initialize` (protocol version `2025-11-25`), then `tools/list`, then `tools/call`. The server's tools were `list_artifacts`, `list_types`, `pin_artifact`, `unpin_artifact` and `publish_version`, each with a JSON schema whose properties were `slug`, `title`, `icon`, `favicon`, `label`, `content`, `base_version`, `contract`, `deadline`, `limit`, `query`, `shared_live`, `shared_only` and `type` as relevant. `list_artifacts` returns `structuredContent{frames[{slug, title, label, rel: mine or shared, audience: owner or public, live, owner_account, owner_email, type_slug, type_title, source_surface, last_edit{chat, code, cowork}, last_viewed_at, created_at, updatedAt, icon, icon_key, tint, description, duplicable, removable, renamable}], starsEnabled, thumbsEnabled}`. A result carries `_meta["anthropic.com/artifact-route"]{status, headers{x-frame-push-remaining}}` so a publish can be rate-limited through it, and a `ttlMs` and `cacheScope` for the list. Tool calls carry `_meta["anthropic.com/artifact-route"]{request_id, attempt_id, entrypoint, publish_context, template, description}`.

### Live sync

`GET /api/frame/sync?slug=<slug>&vn=passive` upgrades to a WebSocket. The client offers `Sec-WebSocket-Protocol: frame-sync.v1,<sync token>` and `Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits`; the server selects `frame-sync.v1` only and negotiates no extension, so frames are uncompressed. The sync token is the second subprotocol: dot-separated fields (the account id base64-encoded, the organisation id, the role `owner_agent`, an issue time and an expiry in epoch seconds, a signature), valid for a quarter of an hour, taken from the `GET /api/frame/{slug}` record. Every message is JSON text `{kind, slug, payload?}`:

| Direction | `kind` | `payload` |
|---|---|---|
| client to server | `activity` | `{busyS}` seconds the agent has been busy |
| client to server | `ping` | none; answered by a server message `pong` |
| server to client | `roster` | `{accountUuids[], agents[{accountUuid, busy?}]}` |
| server to client | `ctrl:joined` | `{door, lane, stores[], sendStores[]}` |
| server to client | `ctrl:invalidate` | `{tag, ver, replay?}`: the page changed; refetch |
| server to client | `pong` | none |

The server also sends WebSocket ping control frames, which the client answers with pong frames. A version string is `<epoch seconds>-<four hex digits>`, the same string the publish answer carries as `version`. On joining, the server sends one `ctrl:invalidate` with `replay: true` naming the current version, then one without `replay` for each later publish, tagged `INVALIDATE_TAG_LIVE`; `ctrl:joined` named the stores the artifact has (`bongo`, and `db` once it declared that capability). The frames a browser page exchanges (database writes, presence, comments) were not observed: a page's traffic does not pass through the rig, and the capture held a single client. Their page-visible API is the declarations above.

### The page runtime

A published page reaches the platform through `claude.use(name)`, which resolves a capability namespace or `null` (a view that cannot run it; pages are told to design for absence). The capability a page declares at publish time (`capabilities: {db: {}}` and so on) is what the server provisions. Each name has a declarations file in the contract:

| Capability | Purpose |
|---|---|
| `artifact` (formerly `self`) | the page's own record: publish a new version of itself, edit a live doc, read metadata |
| `assets` | upload, list and delete binary and text assets with durable ids |
| `comments` | write comment threads on the artifact as the viewer |
| `db` | a persistent realtime document store shared by viewers: slash-separated paths, live subscriptions, access rules keyed on the viewer's sharing level (`view`, `interact`, `admin`, `owner`) |
| `downloads` | offer a generated file to the viewer behind a confirmation |
| `files` | read the files of a Claude Code project the artifact declares, with the viewer's own access |
| `mcp` | call the viewer's connected MCP tools (`callTool`, `watchTool`, `listTools`, `server(name)`) with the viewer's credentials |
| `permissions` | read and request the page's capability permissions (`state`, `request`, `manage`) |
| `room` | everyone viewing now: `emit` and `on` for transient topics, `presence` for shared per-viewer state, and sending a message to the viewer's Claude session |
| `sample` | ask Claude from the page on the viewer's own account (`sample`, `sample.json`, `limits`) |
| `user` | facts about the viewer and the people the shared state refers to |

The page host is a sandboxed origin of the artifact service, not `api.anthropic.com`; a read from the CLI of a published page's content goes there.

## Client-only contracts

### Self-hosted runner

The runner is part of the CLI (`claude self-hosted-runner --api-url <url> --environment-secret-file <path>`), so its whole contract can be exercised against a stand-in server with no Anthropic account; this section is the client's reading of it, confirmed by running the runner against such a stand-in. The server side also requires a Team or Enterprise plan with self-hosted environments allowed for the organisation.

Every runner call carries `Authorization: Bearer <token>`, `anthropic-version: 2023-06-01` and `x-self-hosted-runner-version`. The bearer is the environment secret for `register`, the runner token for the runner routes and the session token for the session routes. Every id in a path, and every id in an answer, must match `^[a-zA-Z0-9_-]+$` and be at most 256 characters.

| Call | Request | Answer the client reads |
|---|---|---|
| `POST /v1/code/runners/self-hosted/runners/register` | `{runner_version, use_anthropic_git_proxy, server_auto_mode_lists: SERVER_AUTO_MODE_LISTS_NO_ALLOW or SERVER_AUTO_MODE_LISTS_NONE, client_label, lock_to_account_id?}` | `{runner_id, runner_token}` |
| `POST .../runners/{runner_id}/poll` | `{available_capacity, wake_source?, warmup_complete?}` | `{assignment_ids[], session_assignments[], lease_expires_at, suggested_poll_interval}` |
| `POST .../sessions/{id}/token` | `{}` | `{session_token, tools_host?}` |
| `GET /v1/code/sessions/{id}/remote` | none | `{sources, push_targets, claude_code_args, environment_variables}`, each defaulting to empty |
| `POST .../sessions/{id}/report-failure` | `{reason, kind or setup_failure_kind, excluded_count?}` | the client reads `stuck` and `excluded_count` |
| `POST .../sessions/{id}/release` | `{}` | the client reads `released` |
| `POST .../deregister` | `{reason, drain_hold, outcome, held_ms, busy_session_ids_at_release}` | none read |
| `POST /v1/code/auth/refresh` | none | `{token}` |

`poll` answers: `assignment_ids` must be an array of valid ids or the whole response is rejected as malformed; `session_assignments` is read only as an array of `{session_id, client_platform?}` where an item without a non-empty string `session_id` is skipped and a `client_platform` matching `^[A-Za-z0-9_.-]{1,64}$` labels the session in the runner's metrics (any other value is logged once and the label falls back to `unknown`); `lease_expires_at` and `suggested_poll_interval` are kept only when strings. Three consecutive `404` answers make the runner drain and exit as "runner record gone server-side".

`tools_host`, when present, must decode as `{tool_server_hosting: integer of at least 1 (a digit string is converted), api_base_url: non-empty string, cwd?: string or null}`; one that fails the schema fails the call with "response holds a tools_host that this runner cannot read". Absent or null, only the session token is returned.

After the token and the remote configuration, the runner clones the sources, starts a child session, and the child speaks the worker family of "Remote Control and session workers" above (`worker/register` answering `worker_epoch`, events, `PUT worker`, heartbeat, diagnostics). The orchestrator variant adds `spawn-hints/poll` and `spawn-hints/nack`, and `--teleport` lists environments through `pools`.

| Action | Call | Notes |
|---|---|---|

### Channels

An MCP server pushes inbound messages into a running session. The server declares `capabilities.experimental["claude/channel"]` and sends `notifications/claude/channel` with `{content: string, meta?: Record<string, string>}`; meta keys not matching `^[a-zA-Z_][a-zA-Z0-9_]*$` are dropped with a warning, and the model sees the message as a `<channel source="<server>" key="value">` element, queued as a meta prompt at priority `next` that is never a slash command and carries no attachments, with a warning that its content is untrusted external data. A server that also declares `claude/channel/permission` is sent `notifications/claude/channel/permission_request` with `{request_id (five letters), tool_name, description, input_preview}` and answers with `notifications/claude/channel/permission` carrying `{request_id, behavior: "allow" or "deny"}`; the terminal dialog races that answer and the first wins. Channels are inbound only: a server replies through its own tools.

`--channels` takes `plugin:<name>@<marketplace>` or `server:<name>` entries, and `--dangerously-load-development-channels` (behind a confirmation dialog) loads servers off the allowlist. The managed settings are `channelsEnabled` (the organisation's opt-in, default off for Team and Enterprise logins) and `allowedChannelPlugins` (`[{marketplace, plugin}]`, replacing the default allowlist, which comes from a feature flag). The SDK control request `channel_enable {serverName}` works for connected plugin-sourced servers only. The gate runs per server connection in this order, each skip with its reason: no capability, a modern protocol revision with no notification path, a third-party provider, the feature turned off (flag or the `allow_channels` policy), `channelsEnabled` not set by a Team or Enterprise organisation, a server not named in `--channels`, a plugin from another marketplace than named, and an entry not on the allowlist; delivery rechecks the policy and flag on every message.

### Voice mode

`/voice` streams microphone audio to `wss://<API host>/api/ws/speech_to_text/voice_stream`, with no WebSocket subprotocol. The query is `encoding=linear16`, `sample_rate=16000`, `channels=1`, `endpointing_ms=300`, `utterance_end_ms=1000`, `language=<code>` (one of twenty codes, default `en`), `use_conversation_engine=true`, and `forward_interims=typed` behind an environment variable or a flag. Headers are `Authorization: Bearer <claude.ai OAuth token>`, `x-app: cli`, `anthropic-client-platform` and `x-config-keyterms` (comma-joined terms, at most 1024 characters and 50 terms, from a fixed list plus the directory name and git branch words).

The client sends `{"type":"KeepAlive"}` on open and every eight seconds, binary frames of raw signed 16-bit little-endian mono PCM at 16 kHz (recorded with a native module or SoX `rec`, buffered until the socket is ready and coalesced to at most 32000 bytes), and `{"type":"CloseStream"}` to finish. It reads JSON text frames: `{"type":"TranscriptInterim" or "TranscriptText","data"}`, `{"type":"TranscriptEndpoint"}`, `{"type":"TranscriptError","description"?,"error_code"?}` and `{"type":"error","message"?}`. After `CloseStream` it waits for an endpoint, a close, five seconds, or 1.5 seconds without data. An upgrade refused with a 4xx status is fatal and never retried; a silent drop replays the buffered audio once; three early failures in ten seconds pause voice input. Gates: a claude.ai OAuth token and the policy `allow_voice_mode`; server-side plan checks are not visible.

### Feedback and shared transcripts

`POST /api/claude_cli_feedback` (30 second timeout, default auth) takes `{"content": "<the payload as one JSON string>", "session_id"?}`. The payload holds `description`, `surface` (`cli`, `ccd`, `ccr`, `ide`, `sdk` or `cowork`), `scope`, `platform`, `gitRepo`, `commitSha`, `terminal`, `version`, `datetime`, `message_count`, the latest assistant message ids, the redacted `transcript`, `errors`, `lastApiRequest` (an allowlist: model, system, tools, tool_choice, betas, max_tokens, thinking, temperature, context_management, output_config), optional `subagentTranscripts`, `rawTranscriptJsonl`, `recentSessionTranscripts`, `debugLog`, and survey fields. The cap is 8 MiB; on a size failure the client resends without the transcript, then without the raw transcript and debug log. A `200` with `feedback_id` is success; a `403` `permission_error` whose message names custom data retention marks a zero-data-retention organisation. `POST /api/claude_code_shared_session_transcripts` (10 second timeout) takes `{"content": "<payload JSON string>", "appearance_id"}` with the payload `{trigger, version, platform, commitSha, lastApiRequest?, transcript, subagentTranscripts?, rawTranscriptJsonl?}`, tries up to four progressively smaller payloads, and succeeds on `200` or `201` with `transcript_id`; triggers are the satisfaction and memory surveys.

Gates, in order: `DISABLE_FEEDBACK_COMMAND`, `DISABLE_BUG_COMMAND`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, the policy `allow_product_feedback` (denied under HIPAA and zero data retention), then a third-party provider or missing Anthropic credentials, which write a local zip bundle (`feedback.json` and `transcript.jsonl` under the configuration directory) and send nothing.

### Local pairing with the browser extension

The CLI and the Chrome extension pair over a local socket (a 4-byte little-endian length prefix per JSON frame) under protocol `claude-local-pairing/v1`, with the CLI as initiator. Attestation: `POST /api/oauth/local_pairing/attest` with `Authorization: Bearer <token>` and `{public_key}` (a fresh P-256 key as an uncompressed point, 87 base64url characters) answers `{assertion}`, an ES256 JWS with `typ` `local-pairing+jwt` and claims `iss, sub, org, azp?, client_kind (desktop or chrome_extension), hybrid, cnf{jkt}, iat, exp, jti?`, `aud` containing `claude-local-pairing/v1`; the CLI checks that `cnf.jkt` is the RFC 7638 thumbprint of its own key and reuses the assertion until 30 seconds before expiry. `GET /api/oauth/local_pairing/jwks.json` answers `{keys[{kty: EC, crv: P-256, kid, x, y}]}`, cached from `Cache-Control`. The handshake messages `offer`, `accept`, `finish` and `done` carry nonces and MACs derived with ECDH P-256 and HKDF-SHA-256 over a transcript hash, after which the channel is sealed with AES-256-GCM, one key per direction and a strictly increasing counter. The peer's assertion must be signed by a published key, carry `client_kind: chrome_extension`, the same `sub`, an allowed `org` and a lifetime of at most 301 seconds. The server-side behaviour of attest and the source of the CLI's own pairing configuration are not in the client.

### Customer-routed inference tokens

The CLI's built-in gateway verifies, and never mints, JWTs of type `cri+jwt` (ES256, issuer `https://api.anthropic.com/api/oauth/cri`, keys at `<issuer>/jwks.json`) on `POST /v1/messages` and `POST /v1/messages/count_tokens`. Claims: `exp, iat, aud, sub, org, scope: "inference"`, optional `act{sub}`; the audience and the organisation must be on the gateway's configured lists, with 60 seconds of clock tolerance and no maximum lifetime. A bad token is `401 authentication_error` and an unobtainable key set is `503` with `retry-after: 30`.

### Managed settings and policy limits

`GET /api/claude_code/settings` answers `{uuid, checksum, settings}` (all required), with a `200`, a `204` or `404` meaning none configured (the client treats a `404` without an Anthropic `request-id` header as an intermediary's answer), and a `304` for a matching `If-None-Match`, whose value is `"sha256:<hex>"` computed by the client over its own cached copy (not the server's `checksum`). The response header `x-claude-code-signature` is an ES256 JWS (`typ` `cc-signed-cache+jws`) stored beside the cache. Requests carry `Cache-Control: no-cache` and the bearer with `anthropic-beta: oauth-2025-04-20` (or `x-api-key`, refused when the base URL is not an Anthropic host); the client times out at ten seconds, retries up to five times, polls hourly, and caches to `remote-settings.json`. Eligibility: Team and Enterprise OAuth logins, any API key, injected tokens, workload-identity profiles and pinned gateways, and OAuth logins with no subscription type; not Pro and Max logins, third-party providers or custom base URLs. A non-empty payload passes a consent dialog for dangerous settings. `forceLoginMethod` and `forceLoginOrgUUID` in the payload refuse a session whose login does not match.

`GET /api/claude_code/policy_limits` answers `{restrictions{<key>: {allowed}}, compliance_taints[], monitoring_notice{text, url?} or null, defaults{...}, core_skills[]}`; the client recognises thirty-odd `allow_*` restriction keys (among them `allow_remote_sessions`, `allow_remote_control`, `allow_channels`, `allow_voice_mode`, `allow_product_feedback`, `allow_web_fetch`, `allow_cobalt_plinth` for Artifacts, `allow_send_file`, `allow_account_skills_sync` and `allow_account_plugins_sync`), denied under the regimes `hipaa` and `zdr`. A `404` means the route is not served and the client fails open for that key; the cache is `policy-limits.json`, polled hourly, with retries at 15, 15, 30, 60, 180 and 600 seconds.

### Ultrareview launch

Gates: the flag `tengu_review_bughunter_config` must have `enabled: true`, the provider must be first-party, the session outside a cloud session, the login a claude.ai subscription with a profile scope, and the policy `allow_remote_sessions` must allow it. `GET /v1/ultrareview/preflight` (header `X-Claude-Code-Session-Id`, five second timeout) answers `{action: "proceed", "confirm" or "blocked", billing_note?, github_login?, confirm?{title?, body}, blocked?{message, action_url, reason?}}`; the client builds its own confirmation text and uses the server's `blocked` message and reason. `GET /v1/ultrareview/quota` is read only for tips.

The launch creates a session with `POST /v1/sessions` (beta `ccr-byoc-2025-07-29`) or, behind a flag, `POST /v1/code/sessions`: the environment is a fixed constant, `tags: ["ultrareview"]`, and the configuration travels as `BUGHUNTER_*` environment variables (a pull request review uses `refs/pull/<n>/head` and no bundle). A branch review builds a git bundle (tiers: all refs, `HEAD`, the current branch, then a squashed single commit; 100 MiB default cap), verifies it, and uploads it with `POST /v1/files` as multipart `file`, `purpose=user_data`, `expires_in_seconds=3600`, sending the returned `id` as `session_context.seed_bundle_file_id`. The client then polls `GET /v1/code/sessions/{id}/events?sort_order=asc&cursor=<last sequence>` every second (answers `{data[{sequence_num, payload}], next_cursor?}`) and `GET /v1/code/sessions/{id}` for `worker_status`. Progress arrives as `<remote-review-progress>{stage, bugs_found, bugs_verified, bugs_refuted}</remote-review-progress>` in hook output and findings as a `<remote-review>` block of JSON that the client passes through unparsed (an array of findings, or `{error, reason?}`). Completion is a `result` event, a findings block, or five idle polls; the wait limit is the configured number of minutes. `POST /v1/code/github/post-review-comment` with `{session_id}` answers `{comment_url, already_posted?}` and posts the review to the pull request from the user's GitHub account. Observed on a three-line change: the create body was `{title: "ultrareview: <branch>", events: [], session_context{sources: [], outcomes: [], seed_bundle_file_id, environment_variables{BUGHUNTER_BASE_BRANCH, BUGHUNTER_DRY_RUN, AUTOPATCH_ENABLE_ASIMOV, BUGHUNTER_CODE_QUALITY, BUGHUNTER_FLEET_SIZE, BUGHUNTER_MAX_DURATION, BUGHUNTER_AGENT_TIMEOUT, BUGHUNTER_TOTAL_WALLCLOCK, BUGHUNTER_RESULT_RELAY_MAX_SEC}}, environment_id, tags: ["ultrareview"]}` (the events list is empty: the review is driven by the environment, not a prompt), and the answer tagged the session `config:auto-create-pr:draft`, `config:review-session` and `ultrareview`. The preflight answered `action: "proceed"`. The session's events were system events of subtype `hook_started`, `hook_progress` and `hook_response` and a final `result` of subtype `success`; the progress tag carried `stage` `finding`, then `verifying`, then `synthesizing` with the three counters, and the findings block was `<remote-review>[{file_path, severity, pr_comment, reasoning, start_line, end_line}]</remote-review>` where `reasoning` ends with a verification note. The review of the small change finished in a couple of minutes.

### Self-hosted environments, from the user and orchestrator side

`GET /v1/code/runners/self-hosted/pools` (beta `ccr-byoc-2025-07-29`) answers `{pools[{pool_id, name, created_at, alive_runner_count?}]}`; the environment picker lists the environments and pools together, and `claude --environment ccpool_<id>` creates a session whose worker field is `self_hosted_runner_pool_id` instead of `environment_id`. The orchestrator calls `POST .../spawn-hints/poll` with `{orchestrator_uuid, hostname, client_version, max, expected_spawn_seconds, min_idle?}`, answered with `{hints[], warm_hints[], pending_count, backing_off_count, circuit_broken_count, pool_pending_session_count, pool_active_session_count, slots}` where each hint carries `jti, session_uuid, attempt, work_order_jwt, sources[{url, revision}], correlation_id, client_platform` and the JWT's claims name the pool and spawn account; and `POST .../spawn-hints/nack` with `{session_uuid, attempt, error (at most 512 characters), retryable, failure_kind?: SESSION_FAILURE_KIND_SPAWN_TIMEOUT or SESSION_FAILURE_KIND_SPAWN_HOOK_ERROR}`. A runner's `report-failure` carries `setup_failure_kind` (`SETUP_FAILURE_KIND_SOURCE_REF_NOT_FOUND`, `..._CHECKOUT_HOOK_TERMINAL`, `..._CHECKOUT_HOOK_TIMEOUT`) or `failure_kind` (`SESSION_FAILURE_KIND_SESSION_CONFIG_ERROR`, `..._RUNNER_CRASH`, `..._ANTHROPIC_CONTROL_PLANE_5XX`), and `deregister` carries `drain_hold{outcome: RUNNER_DRAIN_HOLD_OUTCOME_NOT_NEEDED, _FINISHED or _CAP_EXPIRED, cap_ms, held_ms, busy_session_ids_at_release (at most 64), host_deadline_unix_s?}` and a `reason` of `host_drain`, `shutdown_signal`, `retire_at` or `idle_release`. Runner errors map as: `401` authentication failed, `403` with `error.resource: self_hosted_runners_disabled_by_org` "not enabled for self-hosted environments", `409` with `error.type: session_not_active` (archived or deleted) otherwise an epoch conflict (another runner took over), `429` polling too often; the error body is `{error{type, reason, resource, message}}`.

### Connector proxy and connector sign-in

A connector's tools are called through `https://mcp-proxy.anthropic.com/v1/mcp/{server_id}`: MCP over streamable HTTP (JSON-RPC in POST bodies, JSON or event-stream replies) with the claude.ai OAuth bearer, `X-Mcp-Client-Session-Id` and `Accept-Encoding: identity`. A `401` carrying `X-Mcp-Error-Code` is passed on; any other `401` refreshes the token and retries once. Stateless connectors get no notification stream. Signing in to a connector opens a browser at `https://claude.ai/api/organizations/{org}/mcp/start-auth/{id}?product_surface=<entrypoint>`; the CLI makes no API call for it and reconnects afterwards. The browser and callback legs are on claude.ai and not in the client. The connector directory is `GET /mcp-registry/v0/servers` (described above); behind a flag the client reads `GET /api/directory/servers?limit=500&visibility=<list>[&cursor]` instead, taking entries of type `remote` and their URL.

## What stays unobserved

These parts of the contracts have no capture and no client code that shows them, because the server decides them or they need a second party: the webhook and run calls of routines, the severity values other than `normal`, the browser page's own sync, database and presence frames, the connector sign-in callback, how customer-routed inference tokens are minted, the pairing server's behaviour, the server's authorisation of voice by plan, and the meaning of `uuid` and `checksum` in the managed settings body. Each needs the named counterpart (a Team or Enterprise organisation, a second client, a browser, a microphone, or the server's own source) to be read.
