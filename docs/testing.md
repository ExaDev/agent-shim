# Testing strategy

The full list of cases the resolver, launcher, `check`, `doctor` and shim test suites cover. Verbatim from an earlier README.md.

## Testing strategy

the resolver's cascade and materialisation logic is exactly the kind of thing that's easy to get subtly wrong, so it gets thorough unit tests before anything else is built on it:

- Each cascade layer overriding the last; path overrides beating their parent category
- Directory rules folding correctly for nested paths, and correctly composing configuration profiles mid-tree
- The `secret` category being unconditionally un-overridable — including an explicit `entries` override attempt targeting a `secret`-category file, not only a bare `categories: { secret: true }` toggle, since the two-phase algorithm's usual "entries beat categories" rule does not apply to this one category
- `~/.claude/backups/` never symlinked in under any configuration, matching `secret`; `~/.claude.json` (a sibling of `~/.claude`, not a descendant) never appearing in the resolver's entry manifest at all, confirming it's structurally excluded rather than merely defaulted off
- Committed `.agent-shim.json`/`.agent-shim.local.json` files at different tree depths folding shallowest-to-deepest like local directory rules, composing correctly when both apply to the same directory
- Glob patterns matching correctly against literal `~/.claude/projects/` directory names, never attempting to decode a name back to a real path
- Multi-level and diamond `extends` chains resolving correctly, and a circular `extends` definition (`a` → `b` → `a`) being detected and rejected by the walker rather than looping or stack-overflowing
- One identity producing different resolved states under two different configuration profiles, with no leakage between them
- The exact two-phase merge algorithm: a shallow layer's specific entry surviving a later, deeper layer's blanket category flip on the same category; an exact literal key beating a glob from an earlier layer; two globs from different layers resolving to the later layer's value; two globs from the *same* layer resolving by longest-literal-prefix and then source order; two layers setting the identical category resolving to plain last-layer-wins
- Conditional entries with injectable/fake mtimes, a fake resolved branch, and a fake env snapshot (never real filesystem/git/environment state, so tests aren't time-dependent, git-dependent, or slow) — a `newerThan` condition including a fresh file and excluding a stale one under the same glob, a `branch` condition applying only on a matching branch, an `env` condition applying only when the right variable is set, and a conditionally-matched subtree always being materialised rather than symlinked
- A materialised directory reconciling any real (non-symlink) children written since the last resync back into `~/.claude` before re-deciding, and collapsing back into a plain symlink once its split condition no longer holds
- A `runtime`-category collision between a superseded farm and the current one resolving automatically (`carryOver`'s own `classification` parameter, covered directly, and end-to-end through both `resyncFarm`'s crash-recovery path and `resolveFarmConflicts`'s interactive one) — the decision never calling the caller's `decide`/prompt at all, a genuinely ambiguous collision alongside it in the same superseded farm still reaching that prompt, and the whole auto-resolution falling back to the old fully-manual behaviour when no `classification` is given

`identityManager.ts`, `configProfiles.ts`, `directoryRules.ts`, and `configure.ts` stay thin adapters over the resolver, so most of their correctness rides on the resolver's own test coverage above. The one exception is `listIdentities`, whose own tests cover a deliberate departure from the "throw a validation error and let it propagate" convention: an `identity.json` that is present but unreadable — malformed JSON, or valid JSON this version's `IdentitySchema` rejects — is reported as that one identity's own unreadable entry, so a single bad file never hides every *other* identity from `agent-shim identity list` at the moment they most need to be visible. Only those two content-shaped failures are absorbed; a permission error still propagates. A wholly *absent* `identity.json` remains a silent skip rather than a problem, and both it and `doctor`'s own enumeration filter out directories whose name starts with `.`, since `IdentitySchema` requires an identity name to start with a letter or digit and a resync's own `.<identity>.scratch.<suffix>`/`.<identity>.previous.<suffix>` directories are therefore never identities to report on. `launcher.ts` carries three separately-testable responsibilities of its own that aren't covered by the resolver's purity, and need their own coverage: translating a resolved `Map<path, boolean>` into real filesystem side effects (creating/removing symlinks, materialising/collapsing directories, diffing against the farm's prior state, the per-identity lock and atomic-swap behaviour from [Directory rules](configuration-model.md#directory-rules)) against a fake/in-memory filesystem; invoking the real `claude` binary via an injected `spawn` function (argv/env construction, exit-code propagation), never a real subprocess in a unit test; and the ambient-credential guard — given a fake `process.env`, refusing to proceed when any of the six named variables is set and the active identity's `allowAmbientCredential` is unset/false, proceeding when it's true, and proceeding when `AGENT_SHIM_ALLOW_AMBIENT_CREDENTIAL=1` is set for that one call regardless of the identity's own setting. Provider selection gets the same launcher-level coverage against a fake providers map: the child env gaining the provider's base URL, token, static `env` entries, and no other credential variable; an unknown provider refusing with the known names listed (exit 1); a credential block with no usable source refusing with exit 64; a `--provider` flag beating a cascade-pinned provider; and the guard standing aside for a provider launch (agent-shim supplies the child's credential itself) while still refusing an ambient `ANTHROPIC_AUTH_TOKEN` with no provider selected. Those launcher-level provider cases live in `launcherProvider.test.ts`, which shares its fakes with `launcher.test.ts` through `test-helpers.ts`, and also cover command-backed sources (a fake `CredentialPort` supplies the command's output; a non-zero exit refuses with exit 64 without logging the output, and an interactive source with nobody present refuses without running) and target `apiKey` against `https://api.anthropic.com` with ambient credentials present, with and without headroom. `launcherCredential.test.ts` covers an identity's own credential block the same way: its token exported as `CLAUDE_CODE_OAUTH_TOKEN` and never logged, the guard standing aside for exactly that token already in the environment and still refusing a different one, the block left unresolved when a provider is selected or under the `CLAUDE_CONFIG_DIR` escape hatch, and exit 64 naming the identity and source. `credential.test.ts` covers the resolver itself over the fake port: source order, fall-through, the preset argv, interactive detection (including a 1Password service account), timeouts, a secret file refused for loose permissions with a warning, and summaries that never carry a value; `realPorts.test.ts` runs the real port against a temp file and real child processes for the mode, stderr, timeout and missing-program cases. `providers.test.ts` covers the manager functions (`addProvider`/`listProviders`/`removeProvider`/`loadProvider`) over real temp directories per `identityManager.test.ts`'s convention, plus `resolveProvider` itself as a pure decision over an injected `FsPort` and `CredentialPort`, and the conversion of an old-format provider file into its exact replacement.

Headroom routing keeps the same shape: no real process, port, clock, or HTTP call ever happens in a test. `headroom/ensure.test.ts` drives the launcher-side bring-up against a fake filesystem and scripted supervisor behaviour (first launch spawns the supervisor and waits for its ready state; a healthy daemon is reused without spawning; a dead supervisor pid is replaced, including one that is an unreaped zombie signal 0 still reports alive; a live start lock held by another launcher is waited on while a dead holder's lock is taken over; a fatal `lastError` refuses immediately; a daemon that never appears times out naming the log path; a provider launch is not registered against a daemon whose recorded allowlist hash is not the one the launch needs, waiting for the restart when no live session holds the daemon and refusing, naming the holders, when one does, with a registered session of a dead launcher ignored and a launch that routes no provider not held to the hash at all). `headroom/supervisor.test.ts` runs the whole supervisor loop over injected ports with a clock that only advances when the supervisor sleeps and a process model that keeps signal-0 existence, zombification, and the ChildProcess exit event distinct: install invoked when the binary is missing or the source changed and skipped when the installed version satisfies the source, the spawn allowlist containing every provider plus `api.anthropic.com`, crash restart driven by the exit event while a session is live, a zombie daemon treated as dead and restarted even though existence alone would still report it, the daemon fields cleared from state the moment a crash is detected, an orphan daemon left by a dead predecessor stopped before the successor starts its own, every restart in a generation served on the same socket inside a socket directory created mode 0700, the sockets of dead supervisor generations pruned while a live one's is kept, a refusal recorded as `lastError` (with nothing installed or spawned) on a platform without unix sockets, for a symlinked socket directory, one owned by another user or left group accessible, and a state root too deep for a unix socket path, the backoff schedule and retry budget ending in a recorded `lastError`, drift restarts deferred until the session registry empties, idle shutdown timing (and its reset while sessions are live), and session pruning of dead and zombie launcher pids. `stopSupervisedProcess` gets its own table: never escalating when the process exits on SIGTERM, escalating to SIGKILL once the SIGTERM grace expires, reporting `still-running` when even SIGKILL does not clear it, and sending nothing further when the target is already gone. `headroom/headers.test.ts` covers the `ANTHROPIC_CUSTOM_HEADERS` merge, `headroom/state.test.ts` the state/registry/allowlist primitives (the state file round-tripping the socket path, and a record carrying a TCP port read as malformed), `headroom/socket.test.ts` every refusal the door's socket check makes (another owner, a group or world bit, a symlink, a wrong kind or a missing path, for both the directory and the socket, and a platform without unix sockets), `headroom/commands.test.ts` the spawn arguments (`--uds` and never `--host` or `--port`) and the spawn environment, and `doctor.test.ts` gains the headroom audit cases (never run, malformed state, healthy pids, dead supervisor, a `lastError` warning alongside a running replacement). The launcher's own headroom tests inject a fake `HeadroomPort` to cover the env wiring with and without a provider, the loud refusal when headroom resolved on with no port wired, and that the port is never touched when headroom resolved off.

The credential cache's reported state is tested as a pure function over a fake cache port (`credentialCache.test.ts`: empty, fresh, expired, no expiry, an entry stamped in the future, a store that cannot be read, and that the token never appears in the result) and through `check` and `doctor` (the clause in the text and JSON, a provider's cache alongside an identity's, a block that does not cache and a run with no cache port adding nothing, an unreadable store failing `doctor`). `check.ts`'s three always-on diagnostics get their own tests too, independent of path/cascade resolution: the ambient-credential check against a fake `process.env` (same fixture as `launcher.ts`'s guard, since they share the same detection logic); the settings-secrets advisory against a fake settings.json with populated `env`/`hooks` fields, confirming it reports counts and key names only, never values; and — since Keychain access is real OS state, not something to fake — a manual/integration-only note that the Keychain-name lookup is exercised against a real `security` call in CI on macOS runners, not unit-tested with a mock.

`doctor.ts` deliberately breaks the "throw a validation error and let it propagate" convention every other command file follows, since aggregating every check into one report — rather than aborting on the first broken file — is the whole point of the command. Its own tests cover this directly: every input (identities, configuration profiles, `directory-rules.json`, `config.json`, `categories.local.json`, `active-identity`) fed simultaneously malformed at once, asserting `runDoctor` still returns a full report with one `fail` finding per broken input rather than throwing, plus a genuine `extends` cycle correctly failing and a genuine diamond correctly not being mistaken for one. The PATH-resolution section gets its own coverage for each of its three verdicts at each of the two names it reports on (a shadowed `agent-shim` failing and naming both paths, a not-on-PATH executable warning instead, and an enabled-but-shadowed `claude` shim warning rather than failing), alongside `refinePathShadow`'s own unit tests for the symlink case a directory comparison alone would misreport as a shadow of itself. Its wiring layer sets `process.exitCode` rather than throwing or calling `process.exit()` when the report contains any failure — this is new to the codebase and not unit-tested, matching `registerCheckCommand`'s own I/O wiring being untested for the same reason.

`claudeShim.test.ts` follows `identityManager.test.ts`'s real-temp-directory convention (a fake "own executable" file standing in for the running `agent-shim` binary), rather than `doctor.ts`'s pure-function style, since `enableClaudeShim`/`disableClaudeShim` are themselves real filesystem operations, not something to keep separate from a thin wiring layer. Coverage includes the version-drift case that motivates persisting `claude-shim.json` at all (the source file overwritten in place between two `shim enable` runs, proving the marker — not the inode — is what lets the second run refresh cleanly instead of refusing), a foreign file at the target being refused without `--force` and accepted with it, and the cross-device (`EXDEV`) copy-fallback path via a small injectable `LinkFs` seam (mirroring `config/store.ts`'s own `StoreFs`/`nodeStoreFs` pattern), since a real cross-filesystem rig isn't practical in CI. One test also reproduces Homebrew's actual layout (a symlink into a separate "Cellar" directory) to confirm the shim lands next to the symlink users invoke, not buried in the directory its realpath resolves to. `resolveOwnBinaryCheck`, which feeds `discoverClaudeBinary`'s PATH fallback, is covered in the same file over the same temp layout: a different package's claude beside agent-shim (one npm global prefix) reads as foreign, a `shim enable` hardlink and a symlink to the running binary read as this tool with or without a marker, the recorded target still reads as this tool after version drift, and a `--dir` marker elsewhere does not tar a foreign claude next to agent-shim. The fallback's own loop is covered purely in `versionDiscovery.test.ts`, including the co-location case (a claude in agent-shim's own directory must be found) and the self-reference case (a candidate that is this tool must be skipped, and loud failure when it is the only one), and `doctor.test.ts` runs the real wiring once end to end over a temp prefix to prove `collectDoctorReport` reports the co-located claude.

The codex translation and the front-door daemon that serves it keep the same discipline: no real network (beyond loopback listeners the test itself starts), file, clock or process in a test. `codex/translate.test.ts` covers the pure core against the script it replaces (text, images both ways, tool calls and results linked by call id, long tool names shortened and restored, system turns folded into user turns, the tier mapping's order and overrides, effort levels including omitting reasoning for `none`, the prompt cache key from `metadata.user_id`). `codex/auth.test.ts` drives the `~/.codex/auth.json` store over an injected filesystem and token endpoint: one refresh for any number of concurrent 401s, a re-read before every refresh that reuses a token the Codex CLI already refreshed, rotated tokens merged into the file as it stands, the rotated refresh token on disk before the new access token is handed out, and a refusal that leaves a valid file behind when the persist is killed before the rename. `codex/route.test.ts` covers the translation route itself against a scripted upstream (a stream failure answered as an Anthropic-shaped error, a 429 mapped onto the Anthropic rate-limit surface with retry-after, per-provider translation settings), and `codex/agent.test.ts` pins the keep-alive ceiling at ten seconds against a server whose hint asks for longer. `frontdoor/route.test.ts` covers the identity step (the session split out of the headers, exactly the named internal headers stripped, case-insensitively) and the provider path space; `frontdoor/pipeline.test.ts` covers the ordered pipeline over fakes (backpressure waiting for drain and settling when the client goes away, observers run in order at each response head including unrouted errors, an unauthorized request refused as an Anthropic-shaped 401 before any route is asked, a throwing observer dropped without breaking routing, a route failure answered as an Anthropic-shaped 500 before the head and a destroy after it); `frontdoor/providerRoute.test.ts` covers the per-request provider resolution (a codex provider mounted headroom-eligible with its own address as the hop's upstream, an http provider refused by name until the pass-through route exists, unknown and invalid providers, paths naming no provider), the credential an http provider's route attaches (whatever the child presented replaced by the provider file's own resolved token in the bearer target's header form, an apiKey target answered with x-api-key and the presented bearer dropped, an unresolvable block answered as an Anthropic-shaped 502 naming the provider with nothing forwarded, and a re-resolution after a provider file edit applying to the next request with no restart). `frontdoor/server.test.ts` runs the real listener end to end against a scripted codex upstream: the translation served through the whole stack, the identity and session headers stripped before any route sees the request, a request with no or a wrong launch capability refused 401 without any route being asked, streaming delivered chunk by chunk rather than buffered, the client's disconnect aborting the route, an unrouted target answered as an Anthropic-shaped error, the health probe, and a closed door rebinding the same sticky port so a frozen base URL works again, while a sticky port something else holds is left for a free one without the bind failure reaching the listener's fatal error handler (which used to exit the door, so a replacement could never come up beside a squatter). Its TLS cases use real certificates issued by `x509.ts`: a client that trusts only agent-shim's CA completes a handshake with the provider listener serving the loopback leaf (and the CA-verified health probe passes only against that CA), while the same client cannot talk to a complete door whose leaf a different CA signed, which never sees the request or its credential. serials, IPv6 address forms) and mutating the issuer name was confirmed to fail the tests that name it. `frontdoor/headroomHop.test.ts` builds the door from the production `createDoorPipelines`, with the provider listener on TLS, and runs the hop against a scripted daemon serving on a real unix socket inside a real mode 0700 directory under a throwaway root, reached through the production path from the state file through the socket check to `socketPath`, which forwards by `x-headroom-base-url` the way the real one does (its own `x-headroom-*` controls stripped, every other header verbatim): a streamed response relayed event by event, a process squatting on the old TCP port (named by an earlier release's state file, or by a current state file rewritten with a port) never offered a connection whether the daemon is down or serving, a socket directory left world accessible, a symlinked socket directory and a symlinked socket each refused with a 502 naming the reason and nothing The ordering test discriminates by construction: mutating the pipeline to serve the route before the hop fails three hop tests at once. from the launcher's terminal, and `frontdoor/commands.test.ts` plus `codex/commands.test.ts` the two status commands' output over a fake filesystem. The self-hosted Remote Control surface's worker web proxies are covered at two layers. `frontdoor/rcWebFetch.test.ts` drives the fetch's bounds over an injected dial and resolver: the private-address rule itself (every refused block, the v4-mapped form, and the fail-closed non-address), the environment lift's exact-value vocabulary, the redirect walk answering the final hop's facts with the requested url, the scheme gate that refuses without dialling, the private refusal by name, by literal and mid-redirect (and the lift that dials it), the unresolvable and malformed refusals, the redirect bound (a chain exactly at it settling, one past it refused), the byte cap, the deadline against a hanging dial, the non-2xx refusal naming its status, and the content-type gate carrying the readable families as text while refusing binary; its last case runs the production dial itself against a loopback stand-in, fetching through the door's own agents with the lift set and refusing the loopback without it. `frontdoor/rcSelfHost.test.ts` covers the serving of both endpoints: the worker web-fetch handing the request's one url to the injected fetch and answering the fetched facts, the OAuth bearer refused where the bridge's own JWT is required, the refusal shape answered as a 200 error object (the form the CLI surfaces as the tool's own failure), the framed answer that escapes the reader cap refused rather than sent to be dropped, and the web-search family (the clear refusal naming that no backend ships, the query and domain-filter validation, a wired backend's results, and a wired backend's refusal).
