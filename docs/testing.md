# Testing strategy

The full list of cases the resolver, launcher, `check`, `doctor` and shim test suites cover. Verbatim from an earlier README.md.

## Testing strategy

the resolver's cascade and materialisation logic is exactly the kind of thing that's easy to get subtly wrong, so it gets thorough unit tests before anything else is built on it:

- Each cascade layer overriding the last; path overrides beating their parent category
- Directory rules folding correctly for nested paths, and correctly composing configuration profiles mid-tree
- The `secret` category being unconditionally un-overridable — including an explicit `entries` override attempt targeting a `secret`-category file, not only a bare `categories: { secret: true }` toggle, since the two-phase algorithm's usual "entries beat categories" rule does not apply to this one category
- `~/.claude/backups/` never symlinked in under any configuration, matching `secret`; `~/.claude.json` (a sibling of `~/.claude`, not a descendant) never appearing in the resolver's entry manifest at all, confirming it's structurally excluded rather than merely defaulted off
- Committed `.agent-shim.json`/`.agent-shim.local.json` files at different tree depths folding shallowest-to-deepest like local directory rules, composing correctly when both apply to the same directory
- Glob patterns matching correctly against literal `~/.claude/projects/` directory names, never attempting to decode a name back to a real path
- Multi-level and diamond `extends` chains resolving correctly, and a circular `extends` definition (`a` → `b` → `a`) being detected and rejected by the walker rather than looping or stack-overflowing
- One identity producing different resolved states under two different configuration profiles, with no leakage between them
- The exact two-phase merge algorithm: a shallow layer's specific entry surviving a later, deeper layer's blanket category flip on the same category; an exact literal key beating a glob from an earlier layer; two globs from different layers resolving to the later layer's value; two globs from the *same* layer resolving by longest-literal-prefix and then source order; two layers setting the identical category resolving to plain last-layer-wins
- Conditional entries with injectable/fake mtimes, a fake resolved branch, and a fake env snapshot (never real filesystem/git/environment state, so tests aren't time-dependent, git-dependent, or slow) — a `newerThan` condition including a fresh file and excluding a stale one under the same glob, a `branch` condition applying only on a matching branch, an `env` condition applying only when the right variable is set, and a conditionally-matched subtree always being materialised rather than symlinked
- A materialised directory reconciling any real (non-symlink) children written since the last resync back into `~/.claude` before re-deciding, and collapsing back into a plain symlink once its split condition no longer holds
- A `runtime`-category collision between a superseded farm and the current one resolving automatically (`carryOver`'s own `classification` parameter, covered directly, and end-to-end through both `resyncFarm`'s crash-recovery path and `resolveFarmConflicts`'s interactive one) — the decision never calling the caller's `decide`/prompt at all, a genuinely ambiguous collision alongside it in the same superseded farm still reaching that prompt, and the whole auto-resolution falling back to the old fully-manual behaviour when no `classification` is given

`identityManager.ts`, `configProfiles.ts`, `directoryRules.ts`, and `configure.ts` stay thin adapters over the resolver, so most of their correctness rides on the resolver's own test coverage above. The one exception is `listIdentities`, whose own tests cover a deliberate departure from the "throw a validation error and let it propagate" convention: an `identity.json` that is present but unreadable (malformed JSON, or valid JSON this version's `IdentitySchema` rejects) is reported as that one identity's own unreadable entry, so a single bad file never hides every *other* identity from `agent-shim identity list` at the moment they most need to be visible. Only those two content-shaped failures are absorbed; a permission error still propagates. A wholly *absent* `identity.json` remains a silent skip rather than a problem, and both it and `doctor`'s own enumeration filter out directories whose name starts with `.`, since `IdentitySchema` requires an identity name to start with a letter or digit and a resync's own `.<identity>.scratch.<suffix>`/`.<identity>.previous.<suffix>` directories are therefore never identities to report on. `launcher.ts` carries three separately-testable responsibilities of its own that aren't covered by the resolver's purity, and need their own coverage: translating a resolved `Map<path, boolean>` into real filesystem side effects (creating/removing symlinks, materialising/collapsing directories, diffing against the farm's prior state, the per-identity lock and atomic-swap behaviour from [Directory rules](configuration-model.md#directory-rules)) against a fake/in-memory filesystem; invoking the real `claude` binary via an injected `spawn` function (argv/env construction, exit-code propagation), never a real subprocess in a unit test; and the ambient-credential guard, given a fake `process.env`, refusing to proceed when any of the six named variables is set and the active identity's `allowAmbientCredential` is unset/false, proceeding when it's true, and proceeding when `AGENT_SHIM_ALLOW_AMBIENT_CREDENTIAL=1` is set for that one call regardless of the identity's own setting. Provider selection gets the same launcher-level coverage against a fake providers map: the child env gaining the provider's base URL, token, static `env` entries, and no other credential variable; an unknown provider refusing with the known names listed (exit 1); a credential block with no usable source refusing with exit 64; a `--provider` flag beating a cascade-pinned provider; and the guard standing aside for a provider launch (agent-shim supplies the child's credential itself) while still refusing an ambient `ANTHROPIC_AUTH_TOKEN` with no provider selected. Those launcher-level provider cases live in `launcherProvider.test.ts`, which shares its fakes with `launcher.test.ts` through `test-helpers.ts`, and also cover command-backed sources (a fake `CredentialPort` supplies the command's output; a non-zero exit refuses with exit 64 without logging the output, and an interactive source with nobody present refuses without running) and target `apiKey` against `https://api.anthropic.com` with ambient credentials present, with and without headroom. `launcherCredential.test.ts` covers an identity's own credential block the same way: its token exported as `CLAUDE_CODE_OAUTH_TOKEN` and never logged, the guard standing aside for exactly that token already in the environment and still refusing a different one, the block left unresolved when a provider is selected or under the `CLAUDE_CONFIG_DIR` escape hatch, and exit 64 naming the identity and source. `credential.test.ts` covers the resolver itself over the fake port: source order, fall-through, the preset argv, interactive detection (including a 1Password service account), timeouts, a secret file refused for loose permissions with a warning, and summaries that never carry a value; `realPorts.test.ts` runs the real port against a temp file and real child processes for the mode, stderr, timeout and missing-program cases; `realRunAsyncWithin` is run against real child processes too, for a command that finishes inside the limit (its own status and output), one still running at the limit (stopped, with no status) and one that cannot be started (no status). `providers.test.ts` covers the manager functions (`addProvider`/`listProviders`/`removeProvider`/`loadProvider`) over real temp directories per `identityManager.test.ts`'s convention, plus `resolveProvider` itself as a pure decision over an injected `FsPort` and `CredentialPort`, and the conversion of an old-format provider file into its exact replacement, and a provider file that is not valid JSON, which `listProviders` skips saying so without repeating its text and `readProvider` refuses by name.

`identity list` and `identity show` account details are covered at two levels. `identityAccounts.test.ts` covers the pure pieces over a fake filesystem: the login key two identities share, the grouping that keeps a no-login identity in place, the summary that drops every identifier, the wording, and an unreadable profile reported as a problem rather than thrown. `identityAccountCommands.test.ts` runs the real commands against a throwaway layout with example profiles: the text and `--json` output, an identity with no stored login printing nothing for the fields, identities sharing a login sitting together, one account in two organisations staying apart, and one bad `.claude.json` leaving every other identity listed.

`identity rename` is tested against a temporary state root, a fake Keychain and a fake process table, never the real ones, in files split by subject over one shared fixture (`identityRenameTestWorld.ts`, an installation whose identity is referenced from every place a name is kept). `identityRename.test.ts` renames it and checks each place (the directory and superseded farm, farms of another identity whose name starts the same way left alone, `identity.json`, the farm record, the token file and the credential sources, the cached credential, pools with nested and conditional members, jobs, `acct:` refs in the global block, a profile and a directory rule, the active selection, the usage snapshot, picks and anchors), that no lock is left behind and the report lists what was moved and rewritten in order, that a dry run lists the same steps as the rename, changes nothing, takes no lock and asks the Keychain only for attributes, refuses what needs neither a lock nor a secret (a running session, a name already taken, a usage snapshot that cannot be read or has another schema version) and passes where only the real run can refuse (a lock another resync holds, a login that cannot be read or is too long for one `security -i` line, a cached credential that cannot be read), every refusal of the real run (a running session, a launch not yet spawned and not one of another identity, an unknown or existing name, an unusable or unchanged name, a leftover directory, a token file, a held lock), rollback with a failure injected at a middle step and at the last one, a configuration file that cannot be read stopping before anything changes, comparing the whole tree byte for byte before and after, and that the table of places the state root keeps files (`IDENTITY_NAME_LOCATIONS`) decides every place and marks as rewritten each place a rename changes.

`identityRenameGuards.test.ts` covers the credential file sources other identities and providers hold (re-pointed when they name the moved token file or sit inside the moved directory, the `~` spelling kept, named among the steps in the dry run and the real run, a provider file that cannot be read refused only when it mentions the moved token), a new name that is the old directory under another spelling (refused in both runs, and still refused as existing when the other identity is a different directory), the usage records of the current window (said to keep the old name, and nothing said when there are none), the launch records of a running launcher (refused while it runs, ignored once removed or when the launcher is gone), the signal handling (SIGINT, SIGTERM and SIGHUP between steps rolling every step back with the shell's status for the signal, a signal during the last step letting it finish, one that arrived while the login was read, the handlers removed however it ends, the status for the signal kept when the journal could not be updated or removed, and a login read that ended with no status and no signal still reported as a Keychain failure), and the locks (refreshed between steps, a rollback when one is taken over, taken in name order whichever way round the names are given).

`identityRenameKeychain.test.ts` covers the Keychain cases: the login carried to the service the new directory hashes to and the old item deleted last and only after the new one is looked up, the login never exposed in an argument list, a step, a warning or a thrown error, the login and the cached credential read once and before any lock and not at all when a session is running, a failed write keeping the old login, a later failing step removing the new item, a login already filed under the new directory refused without touching either, no copy for an identity with no login, a failed final delete as a warning, no call to `security` off macOS, and a login too large for one `security -i` line refused with nothing changed (the directory, every file and the old item as they were, and no new item). The same copy was also run against the real `security` on a throwaway keychain file, never the login keychain.
