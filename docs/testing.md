# Testing strategy

The full list of cases the resolver, launcher, `check`, `doctor` and shim test suites cover. Verbatim from an earlier README.md.

## Testing strategy

the resolver's cascade and materialisation logic is exactly the kind of thing that's easy to get subtly wrong, so it gets thorough unit tests before anything else is built on it:

- Each cascade layer overriding the last; path overrides beating their parent category
- Directory rules folding correctly for nested paths, and correctly composing configuration profiles mid-tree
- The `secret` category being unconditionally un-overridable — including an explicit `entries` override attempt targeting a `secret`-category file, not only a bare `categories: { secret: true }` toggle, since the two-phase algorithm's usual "entries beat categories" rule does not apply to this one category
- `~/.claude/backups/` never symlinked in under any configuration, matching `secret`; `~/.claude.json` (a sibling of `~/.claude`, not a descendant) never appearing in the resolver's entry manifest at all, confirming it's structurally excluded rather than merely defaulted off
- Committed `.agent-shim.json`/`.agent-shim.local.json` files at different tree depths folding shallowest-to-deepest like local directory rules, composing correctly when both apply to the same directory
- Glob patterns matching correctly against literal `~/.claude/projects/` directory names, never attempting to decode a name back to a real path
- Multi-level and diamond `extends` chains resolving correctly, and a circular `extends` definition (`a` → `b` → `a`) being detected and rejected by the walker rather than looping or stack-overflowing
- One identity producing different resolved states under two different configuration profiles, with no leakage between them
- The exact two-phase merge algorithm: a shallow layer's specific entry surviving a later, deeper layer's blanket category flip on the same category; an exact literal key beating a glob from an earlier layer; two globs from different layers resolving to the later layer's value; two globs from the *same* layer resolving by longest-literal-prefix and then source order; two layers setting the identical category resolving to plain last-layer-wins
- Conditional entries with injectable/fake mtimes, a fake resolved branch, and a fake env snapshot (never real filesystem/git/environment state, so tests aren't time-dependent, git-dependent, or slow) — a `newerThan` condition including a fresh file and excluding a stale one under the same glob, a `branch` condition applying only on a matching branch, an `env` condition applying only when the right variable is set, and a conditionally-matched subtree always being materialised rather than symlinked
- A materialised directory reconciling any real (non-symlink) children written since the last resync back into `~/.claude` before re-deciding, and collapsing back into a plain symlink once its split condition no longer holds
- A `runtime`-category collision between a superseded farm and the current one resolving automatically (`carryOver`'s own `classification` parameter, covered directly, and end-to-end through both `resyncFarm`'s crash-recovery path and `resolveFarmConflicts`'s interactive one) — the decision never calling the caller's `decide`/prompt at all, a genuinely ambiguous collision alongside it in the same superseded farm still reaching that prompt, and the whole auto-resolution falling back to the old fully-manual behaviour when no `classification` is given

`identityManager.ts`, `configProfiles.ts`, `directoryRules.ts`, and `configure.ts` stay thin adapters over the resolver, so most of their correctness rides on the resolver's own test coverage above. The one exception is `listIdentities`, whose own tests cover a deliberate departure from the "throw a validation error and let it propagate" convention: an `identity.json` that is present but unreadable — malformed JSON, or valid JSON this version's `IdentitySchema` rejects — is reported as that one identity's own unreadable entry, so a single bad file never hides every *other* identity from `agent-shim identity list` at the moment they most need to be visible. Only those two content-shaped failures are absorbed; a permission error still propagates. A wholly *absent* `identity.json` remains a silent skip rather than a problem, and both it and `doctor`'s own enumeration filter out directories whose name starts with `.`, since `IdentitySchema` requires an identity name to start with a letter or digit and a resync's own `.<identity>.scratch.<suffix>`/`.<identity>.previous.<suffix>` directories are therefore never identities to report on. `launcher.ts` carries three separately-testable responsibilities of its own that aren't covered by the resolver's purity, and need their own coverage: translating a resolved `Map<path, boolean>` into real filesystem side effects (creating/removing symlinks, materialising/collapsing directories, diffing against the farm's prior state, the per-identity lock and atomic-swap behaviour from [Directory rules](configuration-model.md#directory-rules)) against a fake/in-memory filesystem; invoking the real `claude` binary via an injected `spawn` function (argv/env construction, exit-code propagation), never a real subprocess in a unit test; and the ambient-credential guard — given a fake `process.env`, refusing to proceed when any of the six named variables is set and the active identity's `allowAmbientCredential` is unset/false, proceeding when it's true, and proceeding when `AGENT_SHIM_ALLOW_AMBIENT_CREDENTIAL=1` is set for that one call regardless of the identity's own setting. Provider selection gets the same launcher-level coverage against a fake providers map: the child env gaining the provider's base URL, token, static `env` entries, and no other credential variable; an unknown provider refusing with the known names listed (exit 1); a credential block with no usable source refusing with exit 64; a `--provider` flag beating a cascade-pinned provider; and the guard standing aside for a provider launch (agent-shim supplies the child's credential itself) while still refusing an ambient `ANTHROPIC_AUTH_TOKEN` with no provider selected. Those launcher-level provider cases live in `launcherProvider.test.ts`, which shares its fakes with `launcher.test.ts` through `test-helpers.ts`, and also cover command-backed sources (a fake `CredentialPort` supplies the command's output; a non-zero exit refuses with exit 64 without logging the output, and an interactive source with nobody present refuses without running) and target `apiKey` against `https://api.anthropic.com` with ambient credentials present, with and without headroom. `launcherCredential.test.ts` covers an identity's own credential block the same way: its token exported as `CLAUDE_CODE_OAUTH_TOKEN` and never logged, the guard standing aside for exactly that token already in the environment and still refusing a different one, the block left unresolved when a provider is selected or under the `CLAUDE_CONFIG_DIR` escape hatch, and exit 64 naming the identity and source. `credential.test.ts` covers the resolver itself over the fake port: source order, fall-through, the preset argv, interactive detection (including a 1Password service account), timeouts, a secret file refused for loose permissions with a warning, and summaries that never carry a value; `realPorts.test.ts` runs the real port against a temp file and real child processes for the mode, stderr, timeout and missing-program cases. `providers.test.ts` covers the manager functions (`addProvider`/`listProviders`/`removeProvider`/`loadProvider`) over real temp directories per `identityManager.test.ts`'s convention, plus `resolveProvider` itself as a pure decision over an injected `FsPort` and `CredentialPort`, and the conversion of an old-format provider file into its exact replacement.

Headroom routing keeps the same shape: no real process, port, clock, or HTTP call ever happens in a test. `headroom/ensure.test.ts` drives the launcher-side bring-up against a fake filesystem and scripted supervisor behaviour (first launch spawns the supervisor and waits for its ready state; a healthy daemon is reused without spawning; a dead supervisor pid is replaced, including one that is an unreaped zombie signal 0 still reports alive; a live start lock held by another launcher is waited on while a dead holder's lock is taken over; a fatal `lastError` refuses immediately; a daemon that never appears times out naming the log path). `headroom/supervisor.test.ts` runs the whole supervisor loop over injected ports with a clock that only advances when the supervisor sleeps and a process model that keeps signal-0 existence, zombification, and the ChildProcess exit event distinct: install invoked when the binary is missing or the source changed and skipped when the installed version satisfies the source, the spawn allowlist containing every provider plus `api.anthropic.com`, crash restart driven by the exit event while a session is live, a zombie daemon treated as dead and restarted even though existence alone would still report it, the daemon fields cleared from state the moment a crash is detected, an orphan daemon left by a dead predecessor stopped before the successor starts its own, the sticky port reused from `lastPort` on start and on every restart while it stays free, a fallback to a fresh port (with the move logged) when the sticky one is occupied, and `lastPort` surviving an idle shutdown to seed the next supervisor generation, the backoff schedule and retry budget ending in a recorded `lastError`, drift restarts deferred until the session registry empties, idle shutdown timing (and its reset while sessions are live), and session pruning of dead and zombie launcher pids. `stopSupervisedProcess` gets its own table: never escalating when the process exits on SIGTERM, escalating to SIGKILL once the SIGTERM grace expires, reporting `still-running` when even SIGKILL does not clear it, and sending nothing further when the target is already gone. `headroom/headers.test.ts` covers the `ANTHROPIC_CUSTOM_HEADERS` merge, `headroom/state.test.ts` the state/registry/allowlist primitives, and `doctor.test.ts` gains the headroom audit cases (never run, malformed state, healthy pids, dead supervisor, a `lastError` warning alongside a running replacement). The launcher's own headroom tests inject a fake `HeadroomPort` to cover the env wiring with and without a provider, the loud refusal when headroom resolved on with no port wired, and that the port is never touched when headroom resolved off.

`check.ts`'s three always-on diagnostics get their own tests too, independent of path/cascade resolution: the ambient-credential check against a fake `process.env` (same fixture as `launcher.ts`'s guard, since they share the same detection logic); the settings-secrets advisory against a fake settings.json with populated `env`/`hooks` fields, confirming it reports counts and key names only, never values; and — since Keychain access is real OS state, not something to fake — a manual/integration-only note that the Keychain-name lookup is exercised against a real `security` call in CI on macOS runners, not unit-tested with a mock.

`doctor.ts` deliberately breaks the "throw a validation error and let it propagate" convention every other command file follows, since aggregating every check into one report — rather than aborting on the first broken file — is the whole point of the command. Its own tests cover this directly: every input (identities, configuration profiles, `directory-rules.json`, `config.json`, `categories.local.json`, `active-identity`) fed simultaneously malformed at once, asserting `runDoctor` still returns a full report with one `fail` finding per broken input rather than throwing, plus a genuine `extends` cycle correctly failing and a genuine diamond correctly not being mistaken for one. The PATH-resolution section gets its own coverage for each of its three verdicts at each of the two names it reports on (a shadowed `agent-shim` failing and naming both paths, a not-on-PATH executable warning instead, and an enabled-but-shadowed `claude` shim warning rather than failing), alongside `refinePathShadow`'s own unit tests for the symlink case a directory comparison alone would misreport as a shadow of itself. Its wiring layer sets `process.exitCode` rather than throwing or calling `process.exit()` when the report contains any failure — this is new to the codebase and not unit-tested, matching `registerCheckCommand`'s own I/O wiring being untested for the same reason.

`claudeShim.test.ts` follows `identityManager.test.ts`'s real-temp-directory convention (a fake "own executable" file standing in for the running `agent-shim` binary), rather than `doctor.ts`'s pure-function style, since `enableClaudeShim`/`disableClaudeShim` are themselves real filesystem operations, not something to keep separate from a thin wiring layer. Coverage includes the version-drift case that motivates persisting `claude-shim.json` at all (the source file overwritten in place between two `shim enable` runs, proving the marker — not the inode — is what lets the second run refresh cleanly instead of refusing), a foreign file at the target being refused without `--force` and accepted with it, and the cross-device (`EXDEV`) copy-fallback path via a small injectable `LinkFs` seam (mirroring `config/store.ts`'s own `StoreFs`/`nodeStoreFs` pattern), since a real cross-filesystem rig isn't practical in CI. One test also reproduces Homebrew's actual layout (a symlink into a separate "Cellar" directory) to confirm the shim lands next to the symlink users invoke, not buried in the directory its realpath resolves to.

The codex translation and the front-door daemon that serves it keep the same discipline: no real network (beyond loopback listeners the test itself starts), file, clock or process in a test. `codex/translate.test.ts` covers the pure core against the script it replaces (text, images both ways, tool calls and results linked by call id, long tool names shortened and restored, system turns folded into user turns, the tier mapping's order and overrides, effort levels including omitting reasoning for `none`, the prompt cache key from `metadata.user_id`). `codex/auth.test.ts` drives the `~/.codex/auth.json` store over an injected filesystem and token endpoint: one refresh for any number of concurrent 401s, a re-read before every refresh that reuses a token the Codex CLI already refreshed, rotated tokens merged into the file as it stands, the rotated refresh token on disk before the new access token is handed out, and a refusal that leaves a valid file behind when the persist is killed before the rename. `codex/route.test.ts` covers the translation route itself against a scripted upstream (a stream failure answered as an Anthropic-shaped error, a 429 mapped onto the Anthropic rate-limit surface with retry-after, per-provider translation settings), and `codex/agent.test.ts` pins the keep-alive ceiling at ten seconds against a server whose hint asks for longer. `frontdoor/route.test.ts` covers the identity step (the session split out of the headers, exactly the named internal headers stripped, case-insensitively) and the provider path space; `frontdoor/pipeline.test.ts` covers the ordered pipeline over fakes (backpressure waiting for drain and settling when the client goes away, observers run in order at each response head including unrouted errors, an unauthorized request refused as an Anthropic-shaped 401 before any route is asked, a throwing observer dropped without breaking routing, a route failure answered as an Anthropic-shaped 500 before the head and a destroy after it); `frontdoor/providerRoute.test.ts` covers the per-request provider resolution (a codex provider mounted headroom-eligible with its own address as the hop's upstream, an http provider refused by name until the pass-through route exists, unknown and invalid providers, paths naming no provider). `frontdoor/server.test.ts` runs the real listener end to end against a scripted codex upstream: the translation served through the whole stack, the identity and session headers stripped before any route sees the request, a request with no or a wrong launch capability refused 401 without any route being asked, streaming delivered chunk by chunk rather than buffered, the client's disconnect aborting the route, an unrouted target answered as an Anthropic-shaped error, the health probe, and a closed door rebinding the same sticky port so a frozen base URL works again, while a sticky port something else holds is left for a free one without the bind failure reaching the listener's fatal error handler (which used to exit the door, so a replacement could never come up beside a squatter). Its TLS cases use real certificates issued by `x509.ts`: a client that trusts only agent-shim's CA completes a handshake with the provider listener serving the loopback leaf (and the CA-verified health probe passes only against that CA), while the same client cannot talk to a complete door whose leaf a different CA signed, which never sees the request or its credential. `frontdoor/x509.test.ts` checks the certificate encoder against Node's own parser (chain verification, issuer matching, host and IP SAN matching, the validity encoding either side of 2050, positive serials, IPv6 address forms) and mutating the issuer name was confirmed to fail the tests that name it. `frontdoor/headroomHop.test.ts` builds the door from the production `createDoorPipelines`, with the provider listener on TLS, and runs the hop against a scripted daemon that forwards by `x-headroom-base-url` the way the real one does (its own `x-headroom-*` controls stripped, every other header verbatim): headroom receiving the Anthropic-shaped request and the translator serving what the daemon forwards back through the direct listener (exactly one daemon request and one upstream call, so the loop cannot double-apply), the project identity re-set on the hop with no session header reaching it, a 502 while the daemon is between restarts, a client disconnect unwinding the hop's own request, and a flag-less session served directly. The credential custody cases: for an http provider, headroom sees only `Bearer agent-shim-sequestered` or `agent-shim-sequestered` and a distinct hop id per request, never the credential, while the provider's upstream receives exactly the header the client sent and none of the door's hop headers; with the daemon holding a hop open, the direct listener refuses an unknown hop id, the wrong generation secret, a live id presented for another provider and a missing id, the upstream seeing none of them, and refuses the same id again once the hop has ended; an OAuth session's bearer reaches the daemon untouched with no hop id. `frontdoor/passthrough.test.ts` runs the pass-through against a fake upstream (the provider prefix stripped with the query kept, the host replaced, internal headers absent, an unreachable upstream answered as an Anthropic-shaped 502), `frontdoor/connect.test.ts` keeps the moved TLS round-trip suite (termination, streaming, blind tunnels, port release), every client in it now presenting a live capability the way a real one derives it from `HTTPS_PROXY`, and adds the surface's authentication and limits over real sockets with the tunnel dialler recording every target: a CONNECT with no credential, a wrong capability, a non-Basic scheme, a repeated header or a credential with no password is answered 407 with the Basic challenge, for the intercept host and a blind-tunnel host alike, and nothing is dialled, intercepted or routed for it; a client that has not finished its head by the deadline gets 408 and is closed while a tunnel established earlier still carries bytes past that deadline; an oversized head gets 431; with the pending cap full of half-sent heads, a newcomer evicts the oldest (408) and a live launch's connection still gets through; an authenticated CONNECT beyond the tunnel cap gets 503 without a dial, and is admitted again once a tunnel closes; and a launch whose registry record is pruned has its open tunnel closed at the next revalidation and its capability refused 407 from then on, using the production check over the real registry functions. Each of those guarantees was checked to discriminate by mutating `connect.ts` (skipping the capability check, never arming the deadline, dropping the eviction, the tunnel cap, the revalidation or the size check on a head whose terminator has arrived): every mutant fails the case naming it. `frontdoor/capability.test.ts` covers the credential itself: the proxy URL percent-encodes a token holding every userinfo delimiter and a client's Basic credential carries it back exactly, the password half is read scheme case-insensitively with colons kept, other schemes and empty or missing passwords present nothing, and only an exact live token is accepted, and `frontdoor/latency.test.ts` bounds the added hop: the median through-door request may cost at most two milliseconds over the direct one, a bound two orders of magnitude above a loopback hop's real cost and still small enough to fail if the hop ever grows a request's worth of work. The ordering test discriminates by construction: mutating the pipeline to serve the route before the hop fails three hop tests at once. The authentication and custody tests were checked the same way: letting the probe skip certificate verification, making `ensureFrontDoor` skip the probe, sending the credential to headroom unsequestered, admitting any hop id, and serving the provider listener without TLS each fail the tests that name that guarantee. The launcher suites cover both launch shapes ending at the right place: a provider session's base URL is the door's HTTPS provider-scoped address with NODE_EXTRA_CA_CERTS on the door's trust bundle and the session headers injected, and an OAuth session keeps its base URL untouched with HTTPS_PROXY on the door's CONNECT surface, carrying the launch's capability as its proxy credential, and the same trust bundle. The parent's own NODE_EXTRA_CA_CERTS reaches the door port, and a bundle warning is logged. `frontdoor/supervisor.test.ts` runs the listener-host lifecycle over injected ports with a clock advanced only by sleeps: all three sticky ports bound and inherited by a successor generation after a crash, moves off occupied ports logged per listener, failed listener starts recorded as `lastError` with the start lock cleared and the already-bound listeners closed, dead sessions pruned, the idle shutdown closing all three listeners and keeping the sticky addresses, and the idle clock reset by a new session. `frontdoor/ensure.test.ts` covers the launcher bring-up (one supervisor under the lock, a dead holder's lock cleared, joining a serving door, a fatal `lastError` refused immediately, a timeout naming the daemon log) and its listener authentication: the listener is verified before anything is registered, a listener failing verification behind a supervisor this launch spawned is refused with the reason and the log named and no session written, and a recorded live pid whose listener fails is distrusted and replaced by a verified supervisor on another port. `frontdoor/probe.test.ts` runs the real synchronous probe against listeners on worker threads (the probe blocks its own thread, so a listener there could never answer): it accepts the loopback leaf from agent-shim's CA and rejects a leaf from another CA for the same names, a leaf from the right CA that does not name 127.0.0.1, a plain-HTTP listener, a closed port, and a squatter that accepts the connection and never answers (failed by the probe's own deadline, not the launcher's outer wait). `frontdoor/trust.test.ts` covers the child's CA bundle: the CA alone when the parent set nothing, a combined bundle that keeps the parent's certificates and is written once per combination, an inherited bundle that already holds the CA reused unchanged, and an unreadable inherited file replaced by the CA alone with a warning naming it. `frontdoor/detach.test.ts` the daemon's independence from the launcher's terminal, and `frontdoor/commands.test.ts` plus `codex/commands.test.ts` the two status commands' output over a fake filesystem. The launcher's own front-door tests inject a fake `FrontDoorPort` to cover the child's base URL, the bring-up order (front door before headroom, since headroom's allowlist needs the door's address), the loud refusal when no port is wired, and that an http provider's launch goes through the door too. `frontdoor/state.test.ts` covers the front-door session registry: a launch whose record carries a capability token is listed (the supervisor's idle decision depends on it, and the supervisor tests register sessions through the real writer for the same reason), the token never appears in a listing, malformed and token-less records are skipped, dead launches are pruned along with their capability, and the registry directory and records are written owner-only; `realPorts.test.ts` proves the real filesystem port produces mode 0700 and 0600 under a permissive umask and narrows entries that already existed wider.

The command surface itself is tested through `buildProgram` (`src/program.test.ts`) against a throwaway `AGENT_SHIM_HOME` layout, scripted prompts and a fake launcher: the verb set each noun exposes, every removed spelling (`rules`, `profile create`, `identity set-default-profile`, `rules add --profile`, `profile set --headroom` and the rest) rejected as a usage error, a runnable example in every command's `--help`, each noun's `add`/`set`/`list`/`show`/`remove`/`use` verbs including `--json` output and `remove`'s `--yes` requirement without a terminal, the terminal-versus-no-terminal split for every prompt, and completion scripts for each shell (the bash one parsed by `bash -n`). `cliError.test.ts` covers `reportFatalError`'s exit statuses and `AGENT_SHIM_DEBUG`; `argv.test.ts` covers `--identity`, `--no-provider`, the boolean launch flags and the `--` terminator; `flags.test.ts` covers the flag, then environment variable, then cascade precedence and the shared boolean vocabulary; and `launcher.test.ts`/`launcherProvider.test.ts` cover the refusal of a missing identity or configuration profile and `--identity` combined with `--provider`.

The usage tracking under `src/usage/` is tested over injected filesystems and a throwaway layout, never the real home. The parsers are covered against real captured header shapes (the unified five-hour and seven-day windows, epoch-second resets, a missing or unparseable field) and the SSE and JSON body scanners against chunk boundaries at every offset, including a split multi-byte character. The store tests assert the new on-disk state: a record appended to its writer's day segment, the snapshot updated with the account's metadata, the newest observation winning whichever order records arrive in, whole-day pruning at the retention boundary, and owner-only modes. The middleware tests assert that a store failure never reaches a request, that door-answered routes are not recorded, that gzip, deflate and brotli bodies are scanned, and that a serialised record holds no prompt, reply or credential content. The command tests drive `usage` and `account show` through the real program, text and `--json`, and an unknown `--identity` fails rather than reading as no usage.

Pool selection is tested at three layers. `rankPool` is a pure function over snapshots, account metadata, log records and a clock, so its tests build `UsageSnapshot` values directly and cover each rule on its own: a window refused until a future reset excludes a member and one past its reset does not, a refusal lapses once a later request went through, a sooner reset outranks more raw headroom, plan size weights the score, an unreadable or missing snapshot ranks as unknown with a reason, pay-per-use ranks after both, the five-hour projection demotes a member at its own pace and at another member's rescaled pace, the last pick holds while its prompt cache is warm and for a resumed conversation, and ties order by name. `poolPick.test.ts` covers loading over a fake filesystem and the last-pick file (round trip, pruning, an unreadable file reported instead of blocking). `launcherPool.test.ts` drives `runLauncher` with `@pool:`, `--identity`, the environment variable and the active-identity file and asserts the spawned `CLAUDE_CONFIG_DIR`, that the front door is engaged by default and by `--no-track-usage` is not, the refusal text and `--wait` against an injected clock and sleep, and the sticky behaviour across two launches over one filesystem. The `pool` command tests run the real program against a throwaway layout, including that `pool pick` records nothing, and `doctor` and `check` have cases for pool members and selectors.
